# 유한의 계단 2,000계단·추락 모션·온라인 1대1 설계

작성일: 2026-09-01  
상태: 작성 완료·사용자 문서 검토 대기

## 1. 목적

기존 웹게임 `유한의 계단`을 다음과 같이 확장한다.

1. 싱글과 온라인 1대1의 최종 목표를 5,000계단에서 2,000계단으로 변경한다.
2. 잘못된 방향으로 이동하면 캐릭터가 빈 방향으로 점프한 뒤 추락하는 모션을 재생한다.
3. 로그인 화면 없이 닉네임과 6자리 방 코드로 친구와 온라인 1대1을 할 수 있게 한다.
4. 현재 공개 주소 `https://foodie-repository.github.io/finite-stairs/`와 기존 QR을 유지한다.
5. 모바일 터치와 PC 키보드 조작을 모두 유지한다.

## 2. 범위

### 포함

- 싱글 모드 2,000계단 엔딩
- 온라인 1대1 생존 레이스
- 방 만들기, 방 코드 복사, 코드로 참가
- 익명 접속과 닉네임
- 동일한 계단 경로와 3초 카운트다운
- 상대 캐릭터의 반투명 실시간 표시
- 계단 수, 방향, 상태, 추락, 결과 동기화
- 연결 끊김 10초 유예 및 재접속
- 같은 방 코드에서 재대결
- 추락 애니메이션과 접근성용 축소 모션
- 모바일·PC 반응형 화면
- 자동 만료되는 방 데이터

### 제외

- 공개 매칭
- 친구 목록과 초대 알림
- 계정 가입 화면
- 채팅과 음성 통화
- 랭킹·전적·승률 저장
- 관전자 모드
- 경쟁 게임 수준의 부정행위 방지

## 3. 확정 게임 규칙

### 공통

- 최종 계단은 2,000이다.
- `ArrowUp` 또는 모바일 `오르기`는 바라보는 방향을 유지하며 한 칸 오른다.
- `Space` 또는 모바일 `전환 + 오르기`는 방향을 반대로 바꾸고 즉시 한 칸 오른다.
- 바뀐 방향이나 현재 방향에 다음 계단이 없으면 추락한다.
- 제한시간이 0이 되면 실패한다.
- 2,000번째 계단에 도달하면 엔딩을 표시한다.

### 온라인 1대1

- 두 플레이어는 같은 시드로 생성한 동일한 계단 경로에서 동시에 시작한다.
- 먼저 추락하거나 제한시간이 끝난 플레이어가 패배한다.
- 누구도 실패하지 않으면 먼저 2,000번째 계단에 도착한 플레이어가 승리한다.
- 무승부는 사용하지 않는다. 거의 동시에 실패해도 Supabase가 먼저 기록한 종료 사건을 기준으로 패자를 결정한다.
- 한 플레이어의 연결이 끊기면 10초를 기다린다. 같은 익명 세션으로 복귀하지 않으면 연결이 끊긴 플레이어가 패배한다.
- 재대결은 두 플레이어가 모두 동의했을 때 같은 방 코드와 새 시드로 시작한다.

## 4. 사용자 흐름

### 싱글

1. 메인 메뉴에서 `싱글 플레이`를 선택한다.
2. 기존 캐릭터 선택과 기록 저장을 사용한다.
3. 2,000계단 도달 시 정상 엔딩과 기록을 표시한다.
4. 오입력 시 추락 모션 뒤 실패 화면을 표시한다.

### 방 만들기

1. 메인 메뉴에서 `친구와 1대1`을 선택한다.
2. 닉네임을 2~12자로 입력한다.
3. `방 만들기`를 누른다.
4. 중복되지 않는 6자리 영숫자 방 코드를 표시한다. 혼동하기 쉬운 `0/O/1/I`는 코드에서 제외한다.
5. 친구가 들어올 때까지 대기한다.
6. 두 플레이어가 준비하면 3-2-1 카운트다운 뒤 서버 시작 시각에 맞춰 경기한다.

### 방 참가

1. 닉네임과 6자리 코드를 입력한다.
2. 코드가 없거나 만료됐으면 오류를 표시한다.
3. 이미 두 명이 들어간 방이면 `방이 가득 찼습니다`를 표시한다.
4. 참가 성공 시 대기실에 들어가고 상대 닉네임과 캐릭터를 표시한다.

## 5. 화면 설계

- 내 캐릭터는 기존 색과 불투명도로 표시한다.
- 상대 캐릭터는 같은 계단 좌표에 약 55% 불투명도로 그린다.
- 화면 상단에 내 닉네임·계단 수와 상대 닉네임·계단 수·연결 상태를 표시한다.
- 상대가 화면에 보이는 계단 범위를 벗어나면 위 또는 아래 방향 표식과 계단 차이를 표시한다.
- 모바일에서는 기존 두 개의 큰 조작 버튼을 유지한다.
- PC에서는 `ArrowUp`과 `Space`를 유지한다.
- 대기실에는 방 코드 복사, 준비, 나가기 버튼을 둔다.
- 결과 화면에는 승리/패배 사유, 두 사람의 계단 수, 재대결, 방 나가기 버튼을 둔다.

## 6. 추락 애니메이션

오입력과 시간 초과는 게임 상태를 즉시 `failed`로 바꾸지 않고 `falling`으로 전환한다.

- 0~200ms: 오입력은 캐릭터가 입력한 빈 방향으로 한 칸 점프하며 위로 살짝 튄다.
- 시간 초과는 현재 바라보는 방향으로 균형을 잃으며 같은 낙하 구간에 들어간다.
- 200~800ms: 몸이 진행 방향으로 기울어지고 회전하며 화면 아래로 가속 낙하한다.
- 추락 중에는 모든 입력을 무시한다.
- 800ms 이후 `failed`로 전환하고 결과 화면을 표시한다.
- 상대에게는 실패 원인, 방향, 시작 시각을 전송해 같은 타이밍의 추락 모션을 재생한다.
- `prefers-reduced-motion` 환경에서는 200ms 이동·페이드로 축소한다.
- 추락 효과음은 모션 시작 시 한 번만 재생한다.

## 7. 시스템 구조

### 프런트엔드

- 현재 GitHub Pages 주소를 유지한다.
- 공개 저장소에 배포 파일만 남아 있으므로, 유지보수 가능한 React/TypeScript 원본 프로젝트를 복원한다.
- 게임 엔진, Canvas 렌더러, 멀티플레이 클라이언트, 방 UI를 분리한다.
- 빌드 결과만 `/finite-stairs/`에 배포한다.

권장 모듈 경계:

- `game/engine.ts`: 계단 생성, 입력, 타이머, 승패 상태
- `game/fallAnimation.ts`: 추락 타임라인 계산
- `render/GameCanvas.tsx`: 내 캐릭터·상대 캐릭터·계단 렌더링
- `multiplayer/roomClient.ts`: 방 RPC와 Realtime 채널
- `multiplayer/protocol.ts`: 네트워크 메시지 타입과 검증
- `screens/MultiplayerLobby.tsx`: 방 만들기·참가·대기실
- `screens/GameScreen.tsx`: 싱글·대전 공통 경기 화면

### Supabase

다른 게임 프로젝트와 권한·데이터가 섞이지 않도록 `finite-stairs-online` 전용 프로젝트를 서울 리전에 만든다. 프로젝트 생성 전 예상 비용을 확인하고 사용자 승인을 받는다.

- 익명 인증을 사용하되 가입 화면은 노출하지 않는다.
- Publishable key만 브라우저에 포함한다.
- Service role key는 브라우저와 GitHub 저장소에 넣지 않는다.
- Realtime Broadcast는 빠른 게임 상태 전송에 사용한다.
- Presence는 온라인·이탈 상태에 사용한다.
- PostgreSQL 테이블과 RPC는 방 생성·참가·경기 시작·최종 승패·재접속 스냅샷에 사용한다.

## 8. 데이터 모델

### `rooms`

- `id uuid primary key`
- `code text unique not null`
- `status text`: waiting, countdown, playing, finished, expired
- `seed bigint not null`
- `match_number integer not null default 1`
- `host_user_id uuid not null`
- `guest_user_id uuid null`
- `start_at timestamptz null`
- `winner_user_id uuid null`
- `loser_user_id uuid null`
- `finish_reason text null`: fall, timeout, goal, disconnect
- `ended_at timestamptz null`
- `expires_at timestamptz not null`
- `version integer not null default 1`

### `room_players`

- `room_id uuid references rooms(id)`
- `user_id uuid`
- `slot smallint`: 1 또는 2
- `nickname text`
- `character_id text`
- `step integer default 0`
- `facing smallint`
- `state text`: waiting, ready, playing, falling, finished, disconnected
- `ready boolean default false`
- `rematch_ready boolean default false`
- `last_seen_at timestamptz`
- 기본 키는 `(room_id, user_id)`
- `(room_id, slot)`은 unique

## 9. 서버 작업과 동시성

다음 작업은 PostgreSQL RPC로 원자적으로 처리한다.

- `create_room(nickname, character_id)`
- `join_room(code, nickname, character_id)`
- `set_ready(room_id)`
- `start_match(room_id)`
- `save_snapshot(room_id, step, facing, state)`
- `report_finish(room_id, reason, step)`
- `claim_disconnect_win(room_id)`
- `request_rematch(room_id)`

`report_finish`는 `rooms.status = playing`일 때 최초 한 번만 종료 상태를 기록한다. 추락·시간 초과는 호출자를 패자로, 목표 도달은 호출자를 승자로 저장한다. 이후 호출은 이미 확정된 결과를 반환한다.

## 10. 실시간 프로토콜

채널 이름은 참여자만 구독할 수 있는 `room:<room-id>` 형식으로 사용한다.

Broadcast 메시지:

- `player_state`: step, facing, state, sequence, sent_at
- `fall_started`: direction, reason, sequence, sent_at
- `ready_changed`
- `countdown_started`: start_at, seed, match_number
- `match_finished`: winner_user_id, loser_user_id, reason
- `rematch_changed`

각 메시지는 방 ID, 경기 번호, 보낸 사용자 ID, 증가하는 sequence를 포함한다. 수신자는 다른 방·이전 경기·낮은 sequence의 메시지를 버린다.

게임 입력은 로컬에서 즉시 처리한 뒤 Broadcast한다. 재접속을 위해 최대 500ms 간격 또는 10계단마다 데이터베이스 스냅샷을 저장한다.

## 11. 보안과 검증

- RLS를 모든 테이블과 private Realtime 채널에 적용한다.
- 참여자는 자신이 참가한 방만 읽을 수 있다.
- 플레이어는 자신의 `room_players` 행만 갱신할 수 있다.
- 방 생성·두 자리 제한·승패 확정은 클라이언트 직접 쓰기가 아닌 RPC에서 처리한다.
- 닉네임은 공백 정리 후 2~12자이며 제어문자와 HTML을 제거한다.
- 방 코드는 서버에서 생성하고 unique 충돌 시 재시도한다.
- RPC는 인증 사용자, 방 참가 여부, 방 상태, 경기 번호를 검사한다.
- casual 1대1 범위이므로 모든 입력을 서버에서 재연산하는 강한 부정행위 방지는 구현하지 않는다.

## 12. 오류와 복구

- Realtime 연결이 잠시 끊기면 `재연결 중`을 표시하고 로컬 입력을 잠근다.
- 동일 익명 세션이 10초 안에 복귀하면 최신 스냅샷과 경기 상태를 받아 재개한다.
- 10초가 지나면 남은 플레이어가 `claim_disconnect_win`을 호출하고, 서버는 상대의 `last_seen_at`을 확인한 뒤 결과를 확정한다.
- 두 사람 모두 연결이 끊기면 승자를 만들지 않고 방을 만료한다.
- 만료된 코드, 가득 찬 방, 잘못된 코드, 중복 참가를 각각 구분해 안내한다.
- Broadcast 유실 시 다음 `player_state`와 데이터베이스 스냅샷으로 복구한다.
- 브라우저를 닫고 다시 열어도 익명 세션과 현재 방 ID가 남아 있으면 재접속을 시도한다.

## 13. 데이터 수명

- 대기 중인 방은 15분 동안 참가가 없으면 만료한다.
- 진행 중 방은 마지막 heartbeat 후 30분이 지나면 만료한다.
- 종료된 방은 10분 동안 재대결을 허용한 뒤 만료한다.
- 만료 행은 예약 작업으로 주기적으로 삭제한다.
- 장기 전적과 채팅 데이터는 저장하지 않는다.

## 14. 테스트 전략

### 단위 테스트

- 경로 길이가 2,001개 지점을 가진다.
- 2,000번째 계단에서 승리한다.
- 방향 전환이 방향 변경과 한 칸 상승을 함께 수행한다.
- 잘못된 입력은 `falling` 상태로 전환한다.
- `falling` 동안 입력을 무시하고 800ms 뒤 `failed`가 된다.
- 시간 초과도 추락 타임라인을 사용한다.
- 동일 시드는 동일 경로를 만든다.
- 낮은 sequence와 이전 경기 메시지를 무시한다.

### 데이터베이스 테스트

- 방 코드는 unique이고 방에는 두 명만 들어간다.
- 세 번째 참가를 거부한다.
- 익명 사용자는 참가하지 않은 방을 읽지 못한다.
- 최초 `report_finish`만 승패를 확정한다.
- 목표 도달·추락·시간 초과·연결 끊김의 승패가 정확하다.
- 10초 이전의 연결 끊김 승리 요청은 거부한다.
- 두 명의 재대결 동의 후에만 경기 번호와 시드를 갱신한다.

### 통합 및 브라우저 테스트

- PC↔PC, PC↔모바일, 모바일↔모바일 조합
- 방 생성, 코드 복사, 참가, 준비, 카운트다운
- 같은 경로와 상대 반투명 캐릭터
- 방향·계단 수·추락 모션 동기화
- 거의 동시 종료 시 한 결과만 확정
- 새로고침 후 10초 이내 재접속
- 10초 초과 연결 끊김 패배
- 재대결과 방 나가기
- 싱글 기록 저장의 회귀 방지
- 공개 GitHub Pages 링크에서 콘솔 오류·레이아웃·터치 입력 확인
